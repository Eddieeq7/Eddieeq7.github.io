Architecture

What a batch of token ids goes through, with tensor shapes.

Attention, written out (no fused kernels)model.py ↗

def forward(self, x):
    B, T, C = x.shape
    q, k, v = self.qkv(x).split(C, dim=2)
    # (B, T, C) → (B, heads, T, head_dim)
    q = q.view(B, T, self.n_head, self.head_dim).transpose(1, 2)
    k = k.view(B, T, self.n_head, self.head_dim).transpose(1, 2)
    v = v.view(B, T, self.n_head, self.head_dim).transpose(1, 2)

    att = (q @ k.transpose(-2, -1)) / math.sqrt(self.head_dim)
    att = att.masked_fill(~self.mask[:, :, :T, :T], float("-inf"))
    att = F.softmax(att, dim=-1)          # each row sums to 1
    att = self.attn_drop(att)

    y = att @ v                           # weighted sum of values
    y = y.transpose(1, 2).contiguous().view(B, T, C)
    return self.resid_drop(self.proj(y))

Why these choices. Pre-norm (LayerNorm before each sublayer) keeps the residual stream clean, so gradients flow through deep stacks without warmup tricks. The output head shares weights with the token embedding, which cuts parameters and makes "reading" and "writing" a token use the same vector. Residual projections start at a smaller scale (std ÷ √2N) so the stream doesn't grow with depth. The causal mask is a fixed lower-triangular buffer: position t can only see positions ≤ t, which is exactly what makes this a decoder.

What the tests prove, rather than assume: changing token 10 leaves the outputs at positions 0–9 bit-identical (the mask works), every attention row sums to 1 with zeros above the diagonal, the hand-written attention matches PyTorch's fused implementation, the initial loss is ≈ ln(V) (an untrained model is uniform), and the model can overfit a single batch to near-zero loss.

    What the sweep showed

    • Context length has a sweet spot at this budget. Going from 32 to 64 to 128 tokens steadily helps (3.007 → 2.891 → 2.818). 256 is worse (2.870), even though each step sees twice the tokens. My read: with learned position embeddings, the far positions get few useful gradient updates in 1,500 steps, and most of the text's structure (a verse line, a speaker turn) fits well inside 128 tokens.
    • Width helps, with diminishing returns. C=128 → 256 drops loss by 0.34. C=256 → 384 drops it by only 0.04 for 2.2× the parameters (7.3M), and the 384-wide model had already begun overfitting by step 1,350. On a 1 MB corpus, the data runs out before capacity does.
    • Learning rate: 3e-4 is clearly too slow (3.089). 3e-3 slightly beats the 1e-3 baseline (2.792 vs 2.818), but that's partly a short-budget effect: a higher rate learns faster early. The full 5,000-step baseline run reached the same 2.793.

    Caveat: most runs were still improving at step 1,500, so this ranks configurations at a fixed short compute budget, not at convergence. Every run's log, plus the script that turns them into this page's data, is in the repo's results/ folder.

    The tokenizer

    Byte-level BPE. It starts from the 256 byte values, so any UTF-8 text encodes and there's no <unk>. It then repeatedly merges the most frequent adjacent pair into a new token. As in GPT-2, text is pre-split by a regex into words, numbers, and punctuation, and merges never cross those boundaries. That also makes training fast: pairs are counted over unique chunks weighted by frequency, not over the whole corpus. Training it takes about 7 seconds.
